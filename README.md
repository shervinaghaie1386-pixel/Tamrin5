فعالیت فصل پنجم: تست، CI/CD و DevOps

نام پروژه: Smart Team Task Manager

مقدمه

در فعالیت‌های قبلی، بخش‌های مختلف پروژه Smart Team Task Manager را بررسی و طراحی کردیم. در فصل دوم با Git و GitHub برای مدیریت تغییرات پروژه آشنا شدیم. در فصل سوم، معماری پروژه و APIهای مربوط به کاربران و وظایف را مشخص کردیم و در فصل چهارم نیز نحوه آماده‌سازی و اجرای Back-End با Docker را بررسی کردیم.

حالا در این فصل می‌خواهیم عملکرد قسمت‌های مختلف پروژه را تست کنیم و ببینیم چطور می‌توان مراحل بررسی و انتشار برنامه را به کمک CI/CD انجام داد.

۱. طراحی پنج Test Case

برای اینکه مطمئن شویم بخش‌های مختلف پروژه درست کار می‌کنند، پنج تست زیر را برای APIهای پروژه در نظر گرفتم:

شماره| مورد آزمایش| نتیجه مورد انتظار
۱| دریافت فهرست وظایف با "GET /api/tasks"| نمایش فهرست وظایف با کد 200
۲| ایجاد وظیفه جدید با "POST /api/tasks" و اطلاعات صحیح| ثبت وظیفه با کد 201
۳| ویرایش اطلاعات یک وظیفه با "PUT /api/tasks/:id"| به‌روزرسانی اطلاعات با کد 200
۴| حذف یک وظیفه با "DELETE /api/tasks/:id"| حذف وظیفه با کد 200
۵| دریافت فهرست کاربران با "GET /api/users"| نمایش فهرست کاربران با کد 200

این پنج مورد برای بررسی عملکرد APIهایی هستند که در فعالیت فصل سوم طراحی کردیم.

۲. طراحی Pipeline

در این پروژه برای بررسی تغییرات و انتشار نسخه‌های جدید، یک Pipeline ساده در نظر می‌گیریم.

مراحل آن به ترتیب زیر است:

Code → Test → Build → Deploy → Monitor

توضیح هر مرحله:

- Code: در این مرحله برنامه‌نویس تغییرات موردنظر را در کد پروژه اعمال می‌کند و آن‌ها را در Git ثبت می‌کند.
- Test: بعد از ارسال تغییرات، تست‌های پروژه اجرا می‌شوند تا از درست کار کردن قسمت‌های مختلف مطمئن شویم.
- Build: اگر تست‌ها با موفقیت انجام شوند، نسخه جدید برنامه آماده می‌شود و Docker Image ساخته می‌شود.
- Deploy: در این مرحله برنامه با استفاده از Docker Container در محیط موردنظر اجرا و منتشر می‌شود.
- Monitor: بعد از انتشار، عملکرد برنامه بررسی می‌شود تا اگر مشکلی وجود داشت، مشخص شود.

در ارتباط با فعالیت فصل دوم، تغییرات ابتدا می‌توانند در Branch مربوط به هر قابلیت ثبت شوند. سپس با استفاده از Pull Request بررسی شده و در صورت تأیید، با Branch اصلی ادغام می‌شوند.

۳. اگر تست با شکست مواجه شود چه اتفاقی می‌افتد؟

فرض کنیم هنگام ثبت یک وظیفه جدید، اطلاعات به‌درستی در سیستم ذخیره نشوند. در این حالت تست مربوط به ثبت وظیفه با شکست مواجه می‌شود.

وقتی چنین اتفاقی بیفتد، Pipeline متوقف می‌شود و اجازه نمی‌دهد برنامه وارد مرحله انتشار شود. ابتدا باید علت خطا پیدا و برطرف شود. سپس تغییرات اصلاح‌شده در Git ثبت می‌شوند و تست‌ها دوباره اجرا خواهند شد.

اگر این بار تست‌ها موفق باشند، مراحل بعدی یعنی Build و Deploy ادامه پیدا می‌کنند.

۴. ارتباط Pipeline با Docker

در فعالیت فصل چهارم، برای اجرای Back-End پروژه از Docker استفاده کردیم و با ساخت Dockerfile، ایجاد Image و اجرای Container آشنا شدیم.

در این فصل نیز Docker یکی از بخش‌های مهم Pipeline است. به این صورت که ابتدا تست‌های برنامه اجرا می‌شوند و اگر نتیجه آن‌ها موفق باشد، از طریق Dockerfile یک Image جدید ساخته می‌شود. سپس با استفاده از این Image، یک Container اجرا شده و برنامه در محیط موردنظر قرار می‌گیرد.

به کمک Docker می‌توان برنامه را در محیطی مشخص و یکسان اجرا کرد و احتمال بروز مشکلاتی که به تفاوت سیستم‌ها و محیط‌های اجرا مربوط هستند، کاهش داد.

نتیجه‌گیری

در این فعالیت، برای پروژه پنج مورد آزمایشی طراحی کردیم و مراحل مختلف یک Pipeline را مشخص کردیم. همچنین بررسی کردیم که در صورت بروز خطا در تست‌ها، فرایند انتشار متوقف می‌شود و بعد از برطرف شدن مشکل ادامه پیدا می‌کند.

در مجموع، Git و GitHub برای مدیریت تغییرات، REST API برای ارتباط بخش‌های پروژه، Docker برای اجرای برنامه و CI/CD برای بررسی و انتشار تغییرات در کنار یکدیگر استفاده می‌شوند.
