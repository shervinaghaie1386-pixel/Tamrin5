 
# **فعالیت فصل پنجم: تست، CI/CD و DevOps**

**نام پروژه: Smart Team Task Manager**

### **مقدمه**

در فصل‌های گذشته، بخش‌های مختلف پروژه Smart Team Task Manager را مرحله‌به‌مرحله طراحی کردیم. در فصل دوم با استفاده از Git و GitHub مخزن پروژه را ایجاد کردیم و برای قابلیت‌های مختلف آن Branch ساختیم، Commit ثبت کردیم و Pull Request انجام دادیم. در فصل سوم منابع پروژه و APIهای مربوط به کاربران و وظایف را مشخص کردیم و برای درخواست‌های مختلف، کدهای وضعیت مناسب در نظر گرفتیم. در فصل چهارم نیز با Docker آشنا شدیم و روش ساخت Image و اجرای Container را بررسی کردیم.

در این فصل قرار است برای همین پروژه چند مورد آزمایشی طراحی کنیم و روند کلی CI/CD را توضیح دهیم تا مشخص شود تغییرات برنامه چگونه بررسی می‌شوند و در صورت وجود خطا چه مراحلی باید طی شود.

### **۱. طراحی Test Caseها**

برای بررسی عملکرد بخش‌های مختلف پروژه، پنج Test Case در نظر گرفته شده است. در هر تست، یک درخواست به API ارسال می‌شود و نتیجه به‌دست‌آمده با نتیجه مورد انتظار مقایسه می‌شود.

**تست اول: دریافت فهرست وظایف**

درخواست: `GET /api/tasks`

نتیجه مورد انتظار: فهرست وظایف ثبت‌شده در سیستم نمایش داده شود و پاسخ با کد وضعیت 200 برگردد.

**تست دوم: ایجاد وظیفه جدید**

درخواست: `POST /api/tasks`

نتیجه مورد انتظار: اگر اطلاعات واردشده معتبر باشد، وظیفه جدید در سیستم ثبت شود و کد وضعیت 201 برگردد.

**تست سوم: ویرایش وظیفه**

درخواست: `PUT /api/tasks/:id`

نتیجه مورد انتظار: اطلاعات وظیفه موردنظر با موفقیت تغییر کند و پاسخ با کد وضعیت 200 برگردد.

**تست چهارم: حذف وظیفه**

درخواست: `DELETE /api/tasks/:id`

نتیجه مورد انتظار: وظیفه انتخاب‌شده از سیستم حذف شود و پاسخ با کد وضعیت 200 برگردد.

**تست پنجم: دریافت اطلاعات کاربران با درخواست نامعتبر**

درخواست: `GET /api/users`

نتیجه مورد انتظار: در صورت ارسال درخواست معتبر، فهرست کاربران نمایش داده شود و کد وضعیت 200 برگردد. همچنین اگر اطلاعات یا پارامترهای ارسالی نامعتبر باشند، سیستم باید متناسب با نوع خطا کد وضعیت 400 را برگرداند.

### **۲. طراحی مفهومی CI/CD Pipeline**

CI/CD به فرایندی گفته می‌شود که در آن تغییرات برنامه به‌صورت مرحله‌به‌مرحله بررسی می‌شوند تا از درست بودن عملکرد آن اطمینان حاصل شود.

برای پروژه Smart Team Task Manager، مراحل اصلی Pipeline به شکل زیر در نظر گرفته می‌شود:

`Push → Install → Test → Build → Report`

در مرحله اول، برنامه‌نویس تغییرات خود را در Git ثبت می‌کند و آن‌ها را به مخزن GitHub ارسال می‌کند. این کار با دستور Push انجام می‌شود.

در مرحله دوم، وابستگی‌ها و کتابخانه‌های موردنیاز پروژه نصب می‌شوند تا محیط اجرای برنامه آماده شود.

در مرحله سوم، تست‌های طراحی‌شده روی بخش‌های مختلف پروژه اجرا می‌شوند تا مشخص شود APIها و قابلیت‌های برنامه درست کار می‌کنند یا خیر.

در مرحله چهارم، اگر تمام تست‌ها با موفقیت انجام شوند، فرایند Build آغاز می‌شود و نسخه قابل اجرا از پروژه آماده خواهد شد.

در مرحله آخر، نتیجه اجرای مراحل در قالب گزارش یا Report نمایش داده می‌شود تا وضعیت موفقیت یا شکست فرایند مشخص باشد.

### **۳. بررسی شکست تست و روش اصلاح خطا**

یکی از بخش‌های مهم CI/CD این است که اگر هنگام اجرای تست‌ها مشکلی به وجود بیاید، سیستم باید از ادامه فرایند جلوگیری کند.

برای مثال، فرض کنیم در پروژه Smart Team Task Manager درخواست ایجاد وظیفه جدید ارسال می‌شود، اما به دلیل وجود یک مشکل در برنامه، به‌جای کد وضعیت 201، کد 500 برگردانده می‌شود.

در این شرایط تست با شکست مواجه می‌شود و Pipeline اجازه ورود به مرحله Build را نمی‌دهد.

برای برطرف کردن مشکل، ابتدا گزارش خطا بررسی می‌شود تا مشخص شود ایراد از کدام قسمت برنامه است. سپس کد مربوطه اصلاح شده و تغییرات جدید در Git ثبت می‌شوند. بعد از ارسال تغییرات به GitHub، تست‌ها دوباره اجرا می‌شوند.

اگر این بار تست‌ها با موفقیت انجام شوند، Pipeline می‌تواند به مرحله بعدی برود.

نکته مهم این است که هر خطایی به معنی شکست تست نیست. برای مثال، اگر درخواست نامعتبر ارسال شود و API به‌درستی کد 400 را برگرداند، این رفتار صحیح است و تست می‌تواند موفق محسوب شود. شکست تست زمانی اتفاق می‌افتد که نتیجه واقعی با نتیجه مورد انتظار مطابقت نداشته باشد.
       ارسال تغییرات به GitHub
                         ارسال تغییرات به مخزن پروژه

                        
                        نمودار مفهومیci/cd 
                         **ارسال تغییرات ← نصب پیش‌نیازها ← اجرای آزمایش‌ها ← بررسی نتیجه آزمایش‌ها ← ساخت نسخه و تصویر داکر ← اجرای برنامه**


                         
در این فرایند، اگر تست‌ها با شکست مواجه شوند، ابتدا خطاها بررسی و اصلاح می‌شوند و سپس تست‌ها دوباره اجرا خواهند شد. اما اگر تست‌ها موفق باشند، پروژه وارد مرحله Build می‌شود.

### **۵. ارتباط CI/CD Pipeline با Docker**

Docker یکی از ابزارهایی است که در مرحله Build و آماده‌سازی برنامه برای اجرا استفاده می‌شود.

در فصل چهارم، برای پروژه Smart Team Task Manager فایل Dockerfile و فایل `.dockerignore` را در نظر گرفتیم و با استفاده از آن‌ها Image پروژه را ساختیم و Container را اجرا کردیم.

در CI/CD نیز می‌توان همین مراحل را به یکدیگر متصل کرد. به این صورت که ابتدا تغییرات برنامه ارسال می‌شوند، سپس تست‌ها اجرا می‌شوند و در صورت موفقیت تمام تست‌ها، Docker Image ساخته می‌شود.

بعد از ساخته شدن Image، می‌توان آن را در محیط موردنظر اجرا کرد و برنامه را در قالب یک Container در دسترس قرار داد.

بنابراین Docker باعث می‌شود برنامه در محیط‌های مختلف با شرایط اجرایی یکسان‌تری اجرا شود و CI/CD نیز کمک می‌کند قبل از انتشار نسخه جدید، تغییرات برنامه بررسی شوند.

نتیجه‌گیری

در این فصل با طراحی Test Case و مفهوم CI/CD آشنا شدیم. متوجه شدیم که تست کردن برنامه قبل از انتشار اهمیت زیادی دارد و در صورت وجود خطا باید ابتدا مشکل شناسایی و اصلاح شود. همچنین ارتباط میان GitHub، تست‌ها، Docker و مراحل انتشار را بررسی کردیم.

در مجموع، فعالیت‌های فصل‌های گذشته به یکدیگر مرتبط هستند؛ به این صورت که ابتدا پروژه را با Git مدیریت می‌کنیم، سپس APIهای آن را طراحی می‌کنیم، با Docker محیط اجرای آن را آماده می‌کنیم و در نهایت با استفاده از تست و CI/CD کیفیت تغییرات را بررسی می‌کنیم.
