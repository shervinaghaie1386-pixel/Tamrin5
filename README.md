### فعالیت فصل پنجم: تست، CI/CD و DevOps

شروین آقائی 
نام پروژه: Smart Team Task Manager

### مقدمه

در فصل‌های گذشته، پروژه Smart Team Task Manager را در چند مرحله طراحی و بررسی کردیم. در فصل دوم با استفاده از Git و GitHub مخزن پروژه را ایجاد کردیم و با مفاهیمی مانند Branch، Commit و Pull Request آشنا شدیم.

در فصل سوم منابع اصلی پروژه، کاربران و وظایف را مشخص کردیم و برای ارتباط با بخش‌های مختلف سیستم، رابط‌های برنامه‌نویسی (API) را طراحی کردیم. همچنین کدهای وضعیت HTTP را برای پاسخ به درخواست‌های مختلف در نظر گرفتیم.

در فصل چهارم نیز با Docker آشنا شدیم و روش ساخت Image، اجرای Container و آماده‌سازی محیط اجرای پروژه را بررسی کردیم.

در فصل پنجم قصد داریم عملکرد بخش‌های مختلف پروژه را با استفاده از Test Case بررسی کنیم. همچنین با مفهوم CI/CD آشنا می‌شویم و توضیح می‌دهیم که چگونه می‌توان مراحل بررسی، ساخت و انتشار برنامه را به‌صورت خودکار انجام داد.

### ۱. طراحی موارد آزمایش (Test Cases)

برای اطمینان از عملکرد صحیح پروژه، پنج مورد آزمایش طراحی می‌کنیم. هدف از این آزمایش‌ها بررسی درخواست‌های مختلف، کنترل پاسخ‌های سیستم و شناسایی مشکلات احتمالی است.

در هر آزمایش، یک درخواست به سیستم ارسال می‌شود و نتیجه واقعی با نتیجه مورد انتظار مقایسه خواهد شد.

جدول طراحی آزمایش‌ها

| شماره | Test Case                    | API Endpoint          | Expected Result |
| ----- | ---------------------------- | --------------------- | --------------- |
| ۱     | دریافت فهرست وظایف           | GET /api/tasks        | 200 OK          |
| ۲     | ایجاد وظیفه جدید             | POST /api/tasks       | 201 Created     |
| ۳     | ویرایش وظیفه                 | PUT /api/tasks/:id    | 200 OK          |
| ۴     | حذف وظیفه                    | DELETE /api/tasks/:id | 200 OK          |
| ۵     | ثبت وظیفه با اطلاعات نامعتبر | POST /api/tasks       | 400 Bad Request |

توضیح آزمایش‌ها

آزمایش اول: دریافت فهرست وظایف

در این آزمایش، درخواست دریافت فهرست وظایف به سیستم ارسال می‌شود. اگر درخواست به‌درستی پردازش شود، اطلاعات وظایف ثبت‌شده نمایش داده شده و کد وضعیت ۲۰۰ برگردانده می‌شود.

آزمایش دوم: ایجاد وظیفه جدید

در این مرحله، اطلاعات یک وظیفه جدید به سیستم ارسال می‌شود. اگر اطلاعات معتبر باشند، وظیفه در سیستم ثبت شده و کد وضعیت ۲۰۱ برگردانده می‌شود.

آزمایش سوم: ویرایش وظیفه

در این آزمایش، اطلاعات یکی از وظایف موجود تغییر داده می‌شود. سیستم باید اطلاعات جدید را ذخیره کند و کد وضعیت ۲۰۰ را برگرداند.

آزمایش چهارم: حذف وظیفه

در این مرحله، درخواست حذف یک وظیفه مشخص ارسال می‌شود. اگر عملیات با موفقیت انجام شود، وظیفه از سیستم حذف شده و پاسخ مناسب برگردانده می‌شود.

آزمایش پنجم: ارسال اطلاعات نامعتبر

در این آزمایش، اطلاعات ناقص یا نامعتبر برای ایجاد یک وظیفه ارسال می‌شود. سیستم باید از ثبت اطلاعات نامعتبر جلوگیری کند و کد وضعیت ۴۰۰ را برگرداند.

نکته: اگر سیستم دقیقاً همان پاسخی را برگرداند که انتظار داریم، آزمایش موفق محسوب می‌شود؛ حتی اگر پاسخ مورد انتظار یک کد خطا مانند ۴۰۰ باشد.

### ۲. آشنایی با CI/CD و طراحی Pipeline

CI/CD یکی از روش‌های مهم در توسعه نرم‌افزار است که کمک می‌کند تغییرات برنامه به‌صورت منظم بررسی شوند و مراحل آماده‌سازی و انتشار آن با دخالت کمتر انسان انجام شود.

این مفهوم از دو بخش اصلی تشکیل شده است:

* Continuous Integration (CI): یعنی تغییرات جدید برنامه به‌صورت مداوم با کد اصلی ترکیب و آزمایش شوند تا مشکلات احتمالی سریع‌تر شناسایی شوند.

* Continuous Delivery / Continuous Deployment (CD): یعنی پس از بررسی و ساخت موفق برنامه، نسخه جدید برای انتشار آماده شود یا به‌صورت خودکار در محیط موردنظر قرار بگیرد.

برای پروژه Smart Team Task Manager، مراحل اصلی فرایند CI به شکل زیر در نظر گرفته می‌شود:

### CI Pipeline

۱. Push

ارسال تغییرات

۲. Install

نصب وابستگی‌ها

۳. Test

اجرای آزمایش‌ها

۴. Build

ساخت نسخه برنامه

۵. Report

نمایش گزارش نهایی

ترتیب مراحل: Push → Install → Test → Build → Report

توضیح مراحل Pipeline

| مرحله | عنوان   | توضیحات                                |
| ----- | ------- | -------------------------------------- |
| ۱     | Push    | ارسال تغییرات برنامه به مخزن GitHub    |
| ۲     | Install | نصب کتابخانه‌ها و وابستگی‌های موردنیاز |
| ۳     | Test    | اجرای آزمایش‌ها و بررسی عملکرد برنامه  |
| ۴     | Build   | ساخت نسخه قابل اجرا از پروژه           |
| ۵     | Report  | تهیه گزارش از نتیجه مراحل              |

در این فرایند، با هر بار ارسال تغییرات جدید به مخزن پروژه، مراحل تعریف‌شده اجرا می‌شوند. اگر آزمایش‌ها موفق باشند، فرایند ساخت نسخه ادامه پیدا می‌کند و نتیجه نهایی در قالب گزارش نمایش داده می‌شود.

### ۳. بررسی شکست آزمایش و روش اصلاح خطا

یکی از مهم‌ترین ویژگی‌های CI/CD شناسایی سریع مشکلات برنامه است. اگر یکی از آزمایش‌ها با شکست مواجه شود، فرایند نباید بدون بررسی مشکل به مرحله بعدی برود.

برای مثال، فرض کنیم در پروژه درخواست ایجاد یک وظیفه جدید ارسال شده است، اما به دلیل وجود مشکل در برنامه، به‌جای پاسخ مورد انتظار، خطای ۵۰۰ دریافت می‌شود.

مقایسه نتیجه مورد انتظار و نتیجه واقعی

| عنوان           | مقدار                     |
| --------------- | ------------------------- |
| API Endpoint    | POST /api/tasks           |
| Expected Status | 201 Created               |
| Actual Status   | 500 Internal Server Error |
| Test Result     | Failed                    |

در این شرایط، آزمایش شکست می‌خورد؛ زیرا نتیجه واقعی با نتیجه مورد انتظار مطابقت ندارد.

مراحل رفع خطا

* ابتدا گزارش خطا (Error Report) بررسی می‌شود تا محل ایجاد مشکل مشخص شود.

* علت خطا در بخش مربوط به برنامه شناسایی می‌شود.

* کدهای معیوب اصلاح می‌شوند.

* تغییرات جدید با استفاده از Git ثبت می‌شوند.

* تغییرات اصلاح‌شده به مخزن GitHub ارسال می‌شوند.

* آزمایش‌ها دوباره اجرا می‌شوند تا از برطرف شدن مشکل اطمینان حاصل شود.

اگر آزمایش‌ها این بار موفق باشند، فرایند می‌تواند به مرحله Build ادامه پیدا کند.

نکته مهم: هر پاسخ خطایی به معنی شکست آزمایش نیست. برای مثال، اگر اطلاعات نامعتبر ارسال شود و سیستم به‌درستی پاسخ ۴۰۰ برگرداند، آزمایش موفق است. شکست زمانی اتفاق می‌افتد که پاسخ واقعی با پاسخ مورد انتظار تفاوت داشته باشد.

### ۴. نمودار مفهومی CI/CD Pipeline

روند کلی اجرای فرایند و نحوه برخورد با شکست آزمایش‌ها در پروژه به شکل زیر است:

```text
ارسال تغییرات به مخزن GitHub
             |
             ↓
       نصب پیش‌نیازها
             |
             ↓
        اجرای آزمایش‌ها
             |
             ↓
       بررسی نتیجه آزمایش
          /       \
      ناموفق       موفق
         |           |
         ↓           ↓
     توقف فرایند   ساخت نسخه
         |           |
         ↓           ↓
     بررسی خطاها   ساخت Docker Image
         |           |
         ↓           ↓
      اصلاح کدها   اجرای برنامه
         |
         ↓
     ارسال تغییرات
         |
         ↓
   اجرای دوباره آزمایش‌ها
```

همان‌طور که در نمودار مشاهده می‌شود، در صورت شکست آزمایش‌ها، ابتدا باید مشکل برطرف شود و سپس آزمایش‌ها مجدداً اجرا شوند. در صورت موفقیت نیز پروژه وارد مراحل ساخت و آماده‌سازی برای اجرا خواهد شد.

### ۵. ارتباط CI/CD Pipeline با Docker

Docker ابزاری برای بسته‌بندی برنامه و وابستگی‌های آن در یک محیط مستقل است. استفاده از آن باعث می‌شود برنامه در سیستم‌ها و محیط‌های مختلف با شرایط اجرایی یکسان‌تری اجرا شود.

در فصل چهارم، با مفاهیم اصلی Docker آشنا شدیم و روش ساخت Image و اجرای Container را بررسی کردیم.

در فرایند CI/CD نیز می‌توان Docker را به مراحل ساخت و انتشار برنامه متصل کرد.

ارتباط مراحل CI/CD با Docker

| مرحله   | ارتباط با Docker                           |
| ------- | ------------------------------------------ |
| Push    | ارسال تغییرات پروژه به GitHub              |
| Install | آماده‌سازی وابستگی‌های موردنیاز            |
| Test    | بررسی عملکرد برنامه پیش از ساخت تصویر      |
| Build   | ساخت Docker Image در صورت موفقیت آزمایش‌ها |
| Report  | نمایش نتیجه ساخت و آزمایش‌ها               |

پس از ساخت Docker Image، می‌توان آن را در محیط موردنظر اجرا کرد و برنامه را در قالب یک Container در دسترس قرار داد.

برای مثال، اگر تمام آزمایش‌های پروژه با موفقیت انجام شوند، فرایند می‌تواند تصویر جدیدی از برنامه بسازد. سپس این تصویر برای اجرای نسخه جدید در محیط موردنظر استفاده می‌شود.

در نتیجه، CI/CD وظیفه بررسی و آماده‌سازی تغییرات را بر عهده دارد و Docker نیز محیط مناسبی برای بسته‌بندی و اجرای برنامه فراهم می‌کند.

### ۶. آشنایی با مفهوم DevOps

DevOps ترکیبی از دو واژه Development و Operations است و به مجموعه‌ای از فرهنگ‌ها، روش‌ها و ابزارها گفته می‌شود که با هدف بهبود همکاری میان تیم توسعه و تیم عملیات به وجود آمده است.

هدف اصلی DevOps افزایش سرعت توسعه، کاهش خطاها و بهبود کیفیت نرم‌افزار است.

مهم‌ترین ویژگی‌های DevOps

| مفهوم               | توضیحات                            |
| ------------------- | ---------------------------------- |
| Collaboration       | همکاری بهتر میان اعضای تیم         |
| Automation          | خودکارسازی کارهای تکراری           |
| Continuous Feedback | دریافت بازخورد سریع از مراحل مختلف |
| Monitoring          | بررسی وضعیت و عملکرد برنامه        |
| Improvement         | بهبود مداوم کیفیت نرم‌افزار        |

چرخه کلی DevOps شامل مراحل زیر است:

`Plan → Code → Build → Test → Deploy → Monitor → Improve`

در این چرخه، ابتدا برنامه‌ریزی انجام می‌شود، سپس کدنویسی و ساخت برنامه صورت می‌گیرد. پس از آزمایش، نسخه جدید منتشر می‌شود و عملکرد آن مورد بررسی قرار می‌گیرد. در نهایت، با توجه به نتایج به‌دست‌آمده، تغییرات و بهبودهای لازم انجام می‌شوند.

### نتیجه‌گیری

در این فصل با مفاهیم Testing، CI/CD و DevOps آشنا شدیم و پنج مورد آزمایش برای بررسی عملکرد بخش‌های مختلف پروژه طراحی کردیم.

همچنین مراحل اجرای CI Pipeline را بررسی کردیم و متوجه شدیم که در صورت شکست آزمایش‌ها، ابتدا باید علت مشکل شناسایی و اصلاح شود و سپس آزمایش‌ها دوباره اجرا شوند.

در ادامه، ارتباط میان CI/CD و Docker را بررسی کردیم و یاد گرفتیم که چگونه می‌توان پس از موفقیت آزمایش‌ها، تصویر جدیدی از برنامه ساخت و آن را در محیط موردنظر اجرا کرد.

در مجموع، فصل‌های مختلف پروژه Smart Team Task Manager به یکدیگر وابسته هستند. ابتدا با Git و GitHub تغییرات پروژه را مدیریت کردیم، سپس APIهای آن را طراحی کردیم، با Docker محیط اجرای برنامه را آماده کردیم و در نهایت با استفاده از Testing و CI/CD کیفیت تغییرات را بررسی کردیم.

این مراحل کمک می‌کنند نرم‌افزار با نظم بیشتر، خطای کمتر و کیفیت بالاتری توسعه پیدا کند.

نکته برای تحویل: این نسخه یک فعالیت مفهومی و مستند است و مطابق توضیحات استاد نیازی به نوشتن کد یا پیاده‌سازی واقعی Pipeline ندارد. جدول‌ها و نمودارها نیز برای روشن‌تر شدن پاسخ فعالیت اضافه شده‌اند.
